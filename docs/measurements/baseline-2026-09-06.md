# Baseline cost report — subagent-driven development

**Date:** 2026-09-06
**Metrics file:** [`baseline-2026-09-06.json`](./baseline-2026-09-06.json) (`groundwork.metrics/2`, anonymised)
**Reproduce:** `plugins/groundwork/scripts/collect-metrics --anonymize`

Every number below is a field in that file. Nothing here is estimated.

## Sample

Three real `subagent-driven-development` executions, harvested from one development machine, all of them the author's own work.

| | |
| --- | --- |
| Transcripts harvested | 63 |
| Attributed to an execution role | 42 runs, 680 turns |
| Unattributed (recon threads, one-off dispatches) | 21 runs, 283 turns |
| Executions | 3 (`execution-1`, `execution-2`, `execution-3`) |
| Tasks | 3, 8, and 5 (execution-1 through execution-3) |
| Wall clock, attributed runs | 165 minutes |

### What this sample is not

**One machine, one author, three executions.** This is a data point, not a distribution. Every execution was Python or TypeScript application work in existing repositories; nothing greenfield, no other language, no other team's conventions, no other controller.

**The executions were not instrumented in advance.** The transcripts survived in the OS temp root and were harvested retroactively, which is exactly the recovery path #13 was built for — but it means the sample is whatever had not yet been deleted, not a deliberately chosen run. Two of the three executions were still in flight when captured.

**The roles are not evenly sampled.** 17 implementer runs against 2 final reviewers. Per-role figures for the final reviewer rest on two runs and should be read as indicative only.

**Model choice was the controller's, not an experiment.** Roles ran on different models by the controller's judgment, so per-role cost differences confound role with model.

## A counting correction that changes the epic's numbers

Claude Code writes **one transcript record per content block** of an assistant message. A message with a thinking block, a text block, and a tool call is three records, each carrying the same `usage`. Counting records as turns therefore counts the same API turn two to five times.

On the longest run in this sample the inflation is **3.4x**: 185 records, 74 actual API turns, 857,821 cache-creation tokens counted against 254,278 actually billed. The collector now accumulates usage per message id, and takes the largest `output_tokens` a message reported, since that field alone varies between a message's records.

This matters beyond a bug fix, because **the epic's stated baseline appears to share the flaw.** Running the old per-record method over this sample reproduces the epic's split almost exactly:

| | uncached input | cache creation | cache read | output | mean turns/run |
| --- | ---: | ---: | ---: | ---: | ---: |
| Epic #8, 48 runs | 0.0% | 54.6% | 41.0% | 4.4% | 31.4 |
| This sample, per-record counting | 0.0% | 52.9% | 42.2% | 4.8% | 35.1 |
| This sample, per-message counting | 0.0% | 41.5% | 48.2% | 10.3% | 16.2 |

The agreement between the first two rows is the evidence. Figures quoted from #8 should be treated as inflated until recomputed.

## The epic's three consequences, tested

**1. "Uncached input is 0.0% of spend." — Holds.** 2,792 tokens across 42 runs. Any optimization aimed at shortening prompts to save input tokens saves nothing.

**2. "Everything present at dispatch time is roughly 7% of cost." — Does not hold. It is 15.5%.** Turn-1 cache write totals 1,111,909 tokens, which is 37.3% of all cache creation, not the 13% the epic assumed, and 15.5% of total cost. Mean turn-1 write is 26,474 tokens.

Still a minority of spend, and most of it is system prompt and tool definitions that cannot be changed — but it is twice what the epic budgeted, and the gap grows for short runs. Task reviewers spend **48.3%** of their cache writes on turn 1; re-reviewers **50.5%**. For a short review dispatch, the floor *is* the cost.

**3. "87% of cache creation happens after turn 1; cost is turns multiplied by resident context." — Directionally right, quantitatively wrong.** 62.7% happens after turn 1, not 87%. Cache read at 48.2% is the largest single class, and it is a pure function of turns times resident context. The mechanism the epic described is real; the number attached to it was not.

## In-run context accumulation, by tool

704 tool calls returned 1,784,661 characters — roughly 446,000 tokens — across attributed runs.

| Tool | Characters returned | Share | Calls |
| --- | ---: | ---: | ---: |
| Read | 965,728 | 54.1% | 144 |
| Bash | 793,840 | 44.5% | 446 |
| Edit | 16,095 | 0.9% | 82 |
| Write | 5,575 | 0.3% | 29 |
| everything else | 3,423 | 0.2% | 3 |

Two tools are 98.6% of everything that flows back into a run. `Read` returns 6,700 characters per call against `Bash`'s 1,780, so `Read` buys more context per call — but 446 Bash calls make it the larger habit.

Read and Bash split differently by role: implementers 53% / 43%, task reviewers 62% / 36%, and the final reviewer 8% / 91% — that last one being a reviewer that worked almost entirely from a pre-built diff file it read through shell commands.

**Tool output does not explain the cache writes.** 446,000 tokens of tool results sit against 1,868,158 tokens of post-turn-1 cache creation. Something else is writing to cache, and it is the finding below.

## The largest controllable cost: fix-round resumes

Cache creation splits three ways:

| | Tokens | Share of cache writes |
| --- | ---: | ---: |
| turn 1 — the dispatch floor | 1,111,909 | 37.3% |
| mid-run prefix rewrites | 473,911 | 15.9% |
| incremental growth turn by turn | 1,394,247 | 46.8% |

The middle row is **six turns**. Six turns, out of 680, wrote 473,911 tokens to cache — **6.6% of the entire measured cost**, and 29.5% of all implementer cache writes. Each is a turn that wrote tens of thousands of tokens while reading *zero* from cache: a full re-write of a context that was already cached.

All six follow the same pattern, with no exceptions in the sample:

| Run | Rewrite | Idle gap before the turn | Time since the coordinator's message |
| --- | ---: | ---: | ---: |
| `a7e235dadd634b21c` | 152,780 | 498s | 28s |
| `a82851d20781ae7e8` | 86,149 | 261s | 4s |
| `aaddd8a4aed0294bb` | 66,307 | 218s | 6s |
| `a1682ccbecc606e0d` | 74,824 | 45s | 2s |
| `a1290d7821feffafb` | 48,192 | 178s | 4s |
| `a1ab4aa3753d8c9ec` | 45,659 | 230s | 4s |

**Every mid-run rewrite in the sample happened within 2 to 28 seconds of the controller resuming that agent with a fix instruction.** The implementer finishes, sits idle while the controller reviews and composes findings, and the resume then re-writes the whole accumulated prefix — an average of 78,985 tokens per resume, on runs whose entire dispatch floor was 26,474.

The 5-minute ephemeral cache TTL is the plausible mechanism for five of the six idle gaps. The 45-second case does not fit that explanation, so the resume itself may also invalidate the prefix. The correlation with the resume is 6 for 6; the mechanism behind it is one hypothesis and not settled here.

## Recommended next ticket

**Reduce the number of fix-round resumes per task by batching findings into one resume.**

The reasoning, all of it traceable above:

- A resume costs an average of 78,985 cache-write tokens — **three times a fresh dispatch's 26,474-token floor.** Resumption is the expensive path, not the cheap one, which inverts the usual intuition.
- 6 resumes cost 6.6% of total spend. Cutting sequential fix rounds from three to one on the execution that used them removes most of it without changing what gets fixed.
- It is structural, not prose. It changes the controller's dispatch shape, which is the insertion point the epic already chose, and it asks no model to be efficient.
- It fails safe. Batching findings into one resume does not skip a review, remove a seat, or reduce what a reviewer looks at. The findings are all still delivered and all still verified.

**What the data does not yet support building.** Dispatch-time context compilation, progressive disclosure, and interface deltas all target turn-1 context, measured here at 15.5% of cost and mostly system prompt. That is more than the 7% the epic assumed and worth revisiting for short review dispatches — where the floor is half the cost — but it remains the smaller lever.

**The honest caveat.** One resume-heavy execution produced all six rewrites. The other two executions dispatched fix work as fresh agents and show none. So the recommendation rests on a single execution's pattern, and the first thing the next ticket should do is confirm the effect appears in a second one.
